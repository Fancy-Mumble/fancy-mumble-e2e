Agent A — Signal cross-client decryption 3 tests

Everything server-side is already proven by wire tests (message relay, SKDM key relay, cert stamping — crates/starling/src/e2e.rs). The fault is in front of the server.
  1. Run the deciding probe first (needs rig, ~10 min): a three-client run with E2E_STARLING_LOG=info,starling_pchat=debug, then grep the server log for certificate=. Three distinct hashes → isolation is fine, move to step 3. Fewer → confirmed: instances share an identity, sender keys collide, and all three tests fall out of one bug.
  2. If shared: fix the isolation. Suspects in order: client e2e_data_dir() honoring FANCY_E2E_DATA_DIR for the cert store specifically; harness ensureDefaultCert racing parallel launches; cert generation being deterministic. The fix is likely small; the diagnosis is the work.
  3. If distinct: instrument the receiving client (RUST_LOG=mumble_tauri=debug reaches the app) and check whether the pchat frame arrives and fails decrypt, or never surfaces to the store. state/handler/ and the signal bridge boundary are yours.

Done when: signal-pchat.multiclient.test.ts is 3/3 twice in a row under the rig lock.

Agent C — Media path 5 suites

The long one — schedule it knowing it outlives the other three. Step-chains mean each suite now fails once, cheaply, so iteration is fast.
  1. Start from screen share: delivery health — the narrowest assertion (frames arrive without freezes) and the one that isolates transport from fps floors. enableFileLogging() is already wired for backend pipeline timings.
  2. Establish where frames die: capture (client), publish (client WebRTC → SFU), forward (crates/sfu), or decode (viewer). One binary-search run per layer with the existing tracing beats reading all four layers.
  3. Only after delivery is green, look at the fps/latency floors — and remember the documented caveat: those floors legitimately fail on software rendering; E2E_SKIP exists for machines where that's the truth.
  4. Camera share shares the broadcaster path; expect it to move with the screen fix, then handle DirectShow-specific remainder separately.

Done when: delivery-health and checkerboard fidelity green; fps suites green or E2E_SKIP-documented for this display, per the existing rule.

Build traps, verified on this box (field reports, 2026-08-09):

  • The libva-2.22 headers under /tmp were cleaned at reboot — builds fail with the known cros-libva E0063 until re-pinned. Read scripts/build-client.sh's own diagnostic instead of hand-rolling: it includes the non-obvious part, that CROS_LIBVA_H_PATH only takes effect after cargo clean -p cros-libva (no rerun-if-env-changed).
  • Anything built inside nix develop (forced here by the broken GTK stack) needs patchelf --set-interpreter /lib64/ld-linux-x86-64.so.2 --set-rpath '$ORIGIN' afterwards. The trap is where the failure surfaces: the build succeeds, then the binary dies on libgbm.so.1 inside .tmp/tauri-driver-*.log, and the harness's error text blames a missing native WebDriver — the wrong place entirely.
  • Iteration shortcut: npm run build in crates/mumble-tauri/ui first, then cargo build -p mumble-tauri --features custom-protocol (debug, ~1.5 min vs ~30 for release) and point E2E_APP_BIN at target/debug/. Patchelf still applies. Ship-grade verification still wants the full build-client.sh.
  • Wayland session: if anything overrides XDG_RUNTIME_DIR, the compositor / D-Bus / PipeWire sockets must stay reachable or GTK init fails — a separate failure from the patchelf one.
  • A killed run leaves WebKitWebDriver processes behind, and the NEXT run then fails with SessionNotCreatedError: Maximum number of active sessions. Reap with pkill -9 -x WebKitWebDriver — under the rig lock, since it reaches every agent.
  • Logs: E2E_STARLING_LOG is the server-side knob; a release-build client needs set_log_to_file {enabled:true} right after launch (set_terminal_logging does not work there).
  • With six sessions running, inotify instances exhaust (default 128) and cargo tauri build dies with "OS file watch limit reached". Use E2E_BUILD_NO_CLI=1 scripts/build-client.sh (plain cargo, no watcher — safe when ui/dist is current), or the user re-persists fs.inotify.max_user_instances=512 (the earlier manual raise reverted at reboot).

Done when: scheduled-messages.multiclient.test.ts 3/3 against the rebuilt client, and a full sweep confirms no suite regressed from the rebuild.

The shared-rig protocol

Four agents, one machine. Diagnosis and code are parallel; verification is serial, and pretending otherwise produces garbage for everyone.

One e2e run at a time, ever. The shared Starling owns TCP+UDP 64738, tauri-driver owns 4445+, and every client window shares the one desktop display — two concurrent runs corrupt each other's focus, ports, and server state.

Rules

  • Rig lock: take it with mkdir /home/sebastian/Documents/projects/fancy-mumble-e2e/.tmp/rig.lock (atomic; write your agent name + intent into rig.lock/owner), release with rm -rf of it when your run ends. If it's held, poll — never kill the holder's processes. A run costs 2–4 min per file; the full sweep 15.
  • pkill is a rig operation. pkill starling / WebKitWebDriver / tauri-driver / mumble-tauri reaches every agent's processes, not yours. Take the lock before any cleanup kill, and prefer killing your own recorded PIDs over pattern kills.
  • Build etiquette: cargo builds of vendor/starling and vendor/client are heavy and share target dirs per tree — announce release builds, and never rebuild while another agent's e2e run is mid-flight (their spawn reads the binary you're replacing).
  • File territories are the table above. Shared harness files (app.ts, page objects, selectors.ts) belong to whoever's step names them; anything else requires a heads-up message first.
  • Never leave a shared harness file in a half-finished state. An uncommitted edit to util/starling.ts renamed the generated TOML's [[virtual_servers]] table to [[instances]] — a name no shipped Starling binary knows — and every agent's StarlingServer.start() died on "unknown field" until it was reverted. A rig-wide outage from one in-flight rename. If a harness change depends on a server change that has not landed in the binary, keep it in your own worktree until both move together.
  • Re-measure before debugging — the house rule that paid for itself three times tonight. After any fix lands anywhere, re-run your file before digging deeper: your bug may already be dead.
  • The two traps that will otherwise eat a day: asserted-on text must be DOM-injected (setReactInputValue — the keymap types - as ß), and WebDriver commands on one session must never run concurrently (ECONNRESET; parallelize across clients, serialize within one).
  • Definition of done, per group: your file(s) green twice in a row under the lock, then one full sweep at the end of the day — npm run e2e with E2E_STARLING_BIN pointed at the current release build — and E2E-STATUS.md updated per landing, not per epoch.

Sequencing that matters

  1. Hour zero: Agent A's cert-grep probe runs first (it needs the rig for ten minutes and its answer may reshape A's whole task). B and C read code and wire-plan meanwhile; D starts the branch rebase, which needs no rig.
  2. D's binary swap is the one cross-group event — schedule it at a natural break, then every agent re-runs their file once against the new artifact before continuing.
  3. C outlives the day by design; A, B, D landing first shrinks the sweep and the red set around it.
  4. End of day: the checkpoint sweep. Iteration sweeps run against dirty trees and say so (the harness stamps +dirty in every run header) — fine for a working signal, not durable: "dirty" is a different tree every hour, and a fix that only exists uncommitted disappears at the next checkout. Once landings stop: owners commit their vendor-tree work, rebuild client + starling from the committed state (build-client.sh, release starling), run one full sweep, and record it in E2E-STATUS with clean hashes — that sweep is the scoreboard; everything before it was navigation.
